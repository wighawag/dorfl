Add the `one-shot` skill: the UNATTENDED conductor that takes one sentence of intent all the way to landed, gated code on the `work/` contract, delegating every rung to a fresh subagent and requiring no runner CLI.

The existing conductors both assume something this case does not have. `drive-tasks` assumes the `dorfl` CLI (it dispatches `do task:<slug> --isolated` per task) and starts from an already-ready board; `orchestrate` assumes a human sitting in the session to answer its batched questions. Neither covers "state a goal, walk away, come back to a reviewable repo" on a machine with no runner installed. `one-shot` fills that hole: it bootstraps the repo when the project does not exist yet, authors the specs, tasks each into vertical tracer bullets, then builds, gates, reviews and lands every task, running to exhaustion rather than to the first question.

The substrate is the harness's subagent facility plus plain `git`. The main session is the conductor and keeps the goal, the state map and every git transition; each rung (spec author, tasker, builder, repairer, reviewer, scout) runs in a fresh child with a self-contained brief and returns a small structured report, which is what keeps the goal session reasoning about the goal after twenty tasks have landed. The builder's brief is the `## Prompt` wrapper from `CLAIM-PROTOCOL.md` used verbatim, so the in-band no-git boundary, the `=== TASK-STOP ===` escape hatch, the `## Decisions` channel and the coherence check all reach the child unmodified.

What makes unattended operation safe is not the gates alone but the mandate and the record. The invocation grants authority to decide anything reversible and internal, to commit the protocol's own transitions, and to ANSWER an item's own `needsAnswers` question when it falls inside that mandate (a flag only a human may ever clear is a deadlock, not a gate, in a run with no human). The working rule is decide, record, continue, with the bar set by reversibility times blast radius rather than difficulty, which is why a greenfield project is near-fully autonomous and an established repo is not. Five things still stop, and each parks one item rather than the run: external consequence (money, publishing, secrets, third parties), destructive reach outside the goal, a fork the goal statement genuinely does not settle, a spent repair budget, and a false premise under the goal itself. Every judgement then lands in one of five auditable homes, none of them the chat log: a transcribed `## Decisions` block in the done record, an ADR in `docs/adr/`, an answer written into the item body as its flag clears, a `work/questions/` sidecar for a refusal, or a `notes/ideas/` note for scope declined.

Three mechanics carry the autonomy. Bootstrap makes `verify` real and green on the empty scaffold BEFORE the first task, because the gate is the entire quality floor and a one-shot whose gate is vacuous produces a night of unverified code. A red gate or blocking review dispatches a fresh repair child at most twice, the second told explicitly to consider that the TASK is wrong rather than the code, then parks (three identical failures is a signal about the task, and grinding produces convincing garbage). Builds run in dependency layers with file-disjoint tasks parallel inside a layer in their own worktrees, landing strictly one at a time with the rebase-and-re-verify land primitive intact.

The goal itself rests durably in `work/notes/ideas/<goal-slug>.md` (the contract's bucket for a proposed pre-spec opportunity), carrying the goal paragraph, the done-when, the scope boundary and the mandate decisions, and it is deleted when the goal is met. It deliberately does NOT list the specs or tasks it spawned: that would be the shared index conflict-safety rule 2 forbids. Each spawned spec carries a `Goal: <goal-slug>` body line instead, and the goal's state is derived on demand by grep plus folder residence, so an interrupted or compacted session re-derives from the tree rather than from memory.

Also routes it in the `work` router, with the three discriminators spelled out: ambition against `from-idea` (which stops at a spec), substrate against `drive-tasks` (which needs the CLI), and presence against `orchestrate` (which batches questions to a human who is there).
