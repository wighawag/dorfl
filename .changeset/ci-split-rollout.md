CI agents now run in a job whose token cannot write. **Re-run `dorfl install-ci` after upgrading, and commit what it writes.**

Why: the `intake` workflow runs an agent with a shell over issue text any GitHub user can write, so a prompt injection has to be assumed. Removing GitHub tokens from the agent's environment (an earlier release) left three routes to the job's write token that no environment scrub can close: the credential `actions/checkout` persists in `.git/config`, the environment of the agent's parent processes, and `sudo` on GitHub-hosted runners. So the generated workflows now run every CI item (an advance item, or an issue for `intake`) as three jobs in `dorfl-item.yml`: `lock` (write token, no agent, no repository code: takes the item's locks at the arbiter's current `main`), `agent` (read-only token, `persist-credentials: false`: runs the agents, the gate and the review, and uploads a handoff instead of pushing) and `apply` (write token, no agent, no repository code: validates the handoff as hostile and does every write). The agent keeps every tool, including its shell; it can still read the provider key and the read token, neither of which can write. Nothing changes on a laptop.

Because all jobs of one workflow run share an artifact namespace, the advance tick no longer uses a matrix: `advance-lifecycle.yml` runs no agent, and a `dispatch` job (`actions: write` only) starts one `dorfl-item-dispatch.yml` run per item. The old `max-parallel` becomes `maxParallel` concurrency slots with `queue: max`. `intake.yml` calls `dorfl-item.yml` with `item: issue:<N>`. The cost: two extra jobs per item, one Actions run per item, and a `dispatch` job per tick (runs waiting in a slot use no runner minutes).

What `install-ci` writes: it regenerates `intake.yml` and `advance-lifecycle.yml`, adds `dorfl-item.yml`, `dorfl-item-dispatch.yml` and a writer-role setup action `.github/actions/dorfl-setup-writer` (Node and dorfl only: no harness, no provider key, no project-setup hook, no cache) next to `.github/actions/dorfl-setup`, which stays the agent role. Existing SHA pins are kept. New pinned actions: `actions/upload-artifact` (v7.0.1) and `actions/download-artifact` (v8.0.1), both to full commit SHAs. The `advance-lifecycle` push trigger is now limited to `main` (older generated workflows fire it on any branch whose push touches `work/questions/**`). `DORFL_GH_TOKEN` needs no change: it now reaches the lock and apply jobs only, and `intake` keeps writing under the built-in token.

Protected paths: CI no longer lands a change to `.github/`, `CODEOWNERS`, `dorfl.json`, `.lfsconfig` or any `.gitattributes`, in either mode. A task that edits one (a workflow-editing task, for instance) goes to needs-attention with a reason naming the path; build it locally (`dorfl do` / `dorfl work-on`). In merge mode a build may also change under `work/` only its own item's transition and new notes.

Merge mode: a lost race on the push to `main` re-rebases and retries but does not re-run the gate, which was always the code's behaviour (the protocol docs, `docs/ci/README.md` and ADR `land-primitive-rebase-reverify-advance` wrongly said it re-gated, and are corrected). What changes is how often it happens: the gate now runs in the agent job minutes before the apply job pushes, so with parallel item runs most merge-mode lands will be re-rebased after the gate ran. Each such land says "`<branch>` landed without re-gate after N lost races" in the apply job's output and carries a `Landed-Without-Regate:` trailer on the landed commit (`git log --format='%h %(trailers:key=Landed-Without-Regate,valueonly)' main` lists them). Propose mode is unaffected.

Old workflows keep working with this version: an agent-spawning verb run without `--phase` in a checkout that persists a credential prints a warning that any agent it launches can read that token (`verify` is exempt). The next minor version turns the warning into a refusal.

A project-setup hook runs in the agent job and must not restore an Actions cache, and self-hosted runners for these workflows must be ephemeral; `docs/ci/README.md` explains both, the three-job shape and the upgrade path.
