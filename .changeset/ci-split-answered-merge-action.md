The CI split where the agent job holds no write token now covers the answered merge action: `advance task:<slug> --phase lock|agent|apply` on an item whose `kind: merge` question is answered no longer refuses. The lock phase takes the advancing lock at the arbiter's `main` and, for a `merge` answer whose kept `work/task-<slug>` carries work `main` lacks, publishes `needsAgent: true` and that branch's tip as `continueTip`; `hold`, `drop` and a `merge` whose branch is absent or already on `main` need no agent job. The agent phase checks the branch out through `createJob` (read-only: its continue rebase is now local, never pushed), runs the optional `strictMergeApproval` re-stale check and the fresh-worktree gate (`prepare` and `verify`) on the rebased tip, and hands over `integrate` with the rebased tip bundled (its Git LFS objects fetched from the arbiter and carried), `merge-restale`, or `needs-attention` (a red gate, with the rebased tip, or a rebase conflict). The apply phase validates the bundle as hostile, pushes its LFS objects first, then the rebased branch leased on `continueTip` (a branch that moved since the lock job writes nothing and keeps the lock), lands it through the unchanged compare-and-swap loop in merge mode (a land after a lost race carries the `Landed-Without-Regate` trailer), and only then records the answer on the new `main`, publishes and releases the lock. `merge-restale` appends the follow-up merge question and re-pauses. `advance --phase` now threads `workspacesDir`, `prepare`, `verify` and `strictMergeApproval` for this; nothing changes without `--phase`.
