# `requeue -m` right after a gate bounce says "no held per-item lock", so the handoff note is lost

Date: 2026-09-29
Observer: conductor of a drive-tasks run over wighawag/webveil (dorfl 0.14.3).

`do task:config-trust-layers --isolated --allow-backlog` failed its acceptance gate and printed "marked 'config-trust-layers' stuck on its per-item lock (surfaced by status; `requeue` once resolved)". Immediately after, `dorfl requeue config-trust-layers --arbiter origin -m "<handoff>"` failed with "has no held per-item lock on origin — nothing to requeue". `git ls-remote` showed no `refs/dorfl/lock/task-config-trust-layers` at that point, only the kept `work/task-config-trust-layers` branch. The following `do` then claimed normally and said "Continuing ... from the kept origin/work/task-config-trust-layers (requeue)", so recovery worked, but the `-m` handoff never reached the agent. Either the stuck lock is not actually written (or is released) on the isolated bounce path despite the message, or requeue looks it up differently. Expected: the lock is held stuck as announced, and `requeue -m` appends the note. At minimum, when no lock is held but a kept branch exists, `requeue -m` could still record the note for the next claim instead of erroring.
