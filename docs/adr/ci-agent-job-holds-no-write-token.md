# ADR: CI agents run in a job whose token cannot write

## Context

dorfl's generated CI workflows ran a `pi` agent with shell tools in jobs holding `contents` / `pull-requests` / `issues: write`, and `intake` runs that agent over issue text any GitHub user can write. Removing GitHub tokens from the agent's environment (`agent-env.ts`) was only a first layer: an agent that shares a job with a write token can still reach it through the credential `actions/checkout` persists in `.git/config`, its parent processes' environment, `sudo` on hosted runners, or state it leaves for dorfl's own writes in the same job. An in-job hardening (snapshot and restore git state around each launch, hooks off, process-group kill, manual LFS push, staging only intended paths) was built, reviewed three times and dropped, because each review found another way through. The root cause is structural: the agent and the token shared a user, a machine and a job.

## Decision

Every CI item runs as three jobs in a workflow run of its own:

1. **lock** (write token, no agent, no repository code): classify the item at the arbiter's current `main`, take its locks, publish trusted facts as job outputs.
2. **agent** (read-only token, `persist-credentials: false`): run the agents, the gate, the Gate-2 review and every local commit as before, stop at the first write, and upload a handoff (a `git bundle` for code-carrying paths, LFS objects, a typed intent record).
3. **apply** (write token, no agent, no repository code, `if: always()`): treat the handoff as hostile, validate it against the trusted lock outputs, then do every write through dorfl's existing seams; release or surface the item when the agent job failed.

Agents keep every tool, including shell. Laptop and non-CI paths keep the single process (no `--phase`).

### Trust model

- The agent controls everything in the agent job: files, processes, the job's outputs, its artifact, its `ACTIONS_RUNTIME_TOKEN` (not in a `run:` step's environment, but measured recoverable from `Runner.Worker` memory with `sudo`; scoped to its own run and job (enforcement inferred from the `scp` claim), so it can upload, and possibly delete, artifacts in that run, and write default-branch cache entries that OTHER runs could restore), and the read token. The design accepts all of that.
- **Trusted channel:** `needs.lock.outputs.*` (set by a job that ran no agent), the event payload, the committed config and tree at the base sha, and whatever the apply job reads from the arbiter itself.
- **Hostile channel:** everything the agent job produces: its artifact, its outputs, its `result`. `needs.agent.result == 'success'` is only a precondition for trying the replay, never evidence that the content is good.
- The gate verdict and the Gate-2 review verdict become attestations from the hostile job. That is no worse than today: the agent can already edit the code and the gate configuration it is judged by. The untrusted-origin safety stays the forced PR (ADR `untrusted-origin-build-checkpoint`), and the apply job recomputes that rule itself (task `ci-split-apply-rejects-hostile-bundle`).
- Accepted residue: the agent can still read and exfiltrate the provider API key, the read token and anything readable with it. Those are not write credentials.
- **The cache is the one cross-run channel.** Runs on the default branch share its Actions cache scope. If item B's agent job restored a cache that item A's agent had poisoned, A would control B's handoff, and in merge mode could land code through B, which is the substitution decision 1 removes. So no generated job restores an Actions cache, agent jobs included; the workflow guard enforces it for everything dorfl generates. A consumer's project-setup hook runs in the agent job and is outside dorfl's control: `docs/ci/README.md` states that it must not restore a cache, and why. A hook that does is the consumer's accepted risk.

### The launch decisions

Recorded as decided on 2026-09-27. The implementation detail these decisions point to lives, verbatim, in the `ci-split-*` tasks (`work/tasks/`), and once they land, in the code.

1. **Binding an artifact to its own item: one workflow run per item** (settled by the spike, finding `github-actions-job-output-key-and-per-run-artifact-isolation`, evidence in `docs/spikes/ci-handoff-key-delivery/`). All jobs of one workflow run share one artifact namespace, and the spike showed that an agent with a shell recovers its job's `ACTIONS_RUNTIME_TOKEN` from `Runner.Worker` memory with `sudo`, so inside one matrix run, item A's agent could plant an artifact under item B's name. A per-item key was measured NOT viable: whatever a job receives through `env:` (the only delivery the no-`${{ }}`-in-`run:` rule allows) is printed in its log, which any authenticated account can read on a public repository, and a masked value is dropped from job outputs. Decided instead: the advance tick dispatches one run of a thin `dorfl-item-dispatch.yml` wrapper per item (`gh workflow run` with `GITHUB_TOKEN` and `actions: write`, measured to work), which calls `dorfl-item.yml` (task `ci-split-generate-workflows` (job shape)). The runtime token is scoped to its own run and job (measured `scp` claim; that the artifact service ENFORCES the scope is inferred from the claim, not tested with a forged request), and two runs upload same-named artifacts without colliding (measured), so "this artifact came from this item's agent job" becomes a property GitHub enforces, with no key and no MAC. Intake already runs one issue per run. The matrix `max-parallel` cap becomes N workflow-level concurrency slots with `queue: max` on the wrapper (task `ci-split-generate-workflows` (job shape)), measured to serialise without cancelling. One channel stays shared across runs: the Actions cache of the default branch, which an agent can write through its runtime token. It is closed by rule, not by the run boundary: no generated job restores a cache, agent jobs included (task `ci-split-generate-workflows` (job shape), the trust model in ADR `ci-agent-job-holds-no-write-token`), and `docs/ci/README.md` tells consumers their project-setup hook must not restore one either.
2. **A lost CAS in the apply job.** The merge-mode retry loop in `performIntegration` re-runs only `rebaseOntoMainWithReconcile` and the push, never the gate (verified). Decided: keep the code's behaviour, and correct the drift in the same change: `WORK-CONTRACT.md` ("Land = rebase + re-verify + advance", in `skills/setup/protocol/` and mirrored to `work/protocol/`), the ADR `land-primitive-rebase-reverify-advance`, and the `advance-lifecycle` template comment ("re-rebase + re-gate + retry"). Re-running the agent phase on a lost race is recorded as a follow-up idea. Stated plainly, because the split changes the numbers: today the fresh gate runs seconds before the first push, so a lost race is rare; after the split the agent job's rebase and gate happen minutes before the apply job's first push (artifact upload, queueing, setup), so with parallel item runs in merge mode `main` will usually have moved, the first push will usually be non-fast-forward, and the landed tree will usually be a re-rebase the gate never saw. The "gated on the rebased tip" property goes from nearly always true to often false in merge mode. Propose mode is unaffected (a human merges the PR, and the repository's own required checks run on it). To keep this visible, the apply phase compares the landed tip's tree with the gated tip's tree and reports "landed without re-gate after N lost races" in the run output and in the landed commit's trailer; task `ci-split-landed-vs-gated-report` implements it and the changeset says the same.
3. **Protected paths.** Decided: a fixed built-in list, not a config key: `.github/`, `CODEOWNERS` (repository root, `docs/`, `.github/`), `dorfl.json`, `.lfsconfig` (added because of decision 6, see task `ci-split-apply-rejects-hostile-bundle`) and `.gitattributes` (added after review: in merge mode a landed `merge=union` or `merge=binary` attribute changes how the apply job's own rebase resolves conflicts, and the CAS loop relies on a real conflict to stop). Plus a `work/` ledger rule for build bundles: the diff under `work/` may contain only this item's own transition, new `work/notes/*` files, and new ADRs; anything else (another item's body, a new file in a pool folder, a sidecar) is rejected in merge mode and listed in the PR body in propose mode.
4. **A legitimate task that edits a protected path** (dorfl's own repository has workflow-editing tasks). Decided: the apply job routes it to needs-attention with a reason that names the protected path and says to build it locally; CI never lands it.
5. **Agent job failed, timed out or was cancelled.** Decided: `failure` and timeout surface the item to needs-attention (sidecar + `needsAnswers: true`, lock released); `cancelled` only releases the lock; for intake every non-success removes the `processing` label and posts nothing. The mechanism is measured (finding `github-actions-job-timeout-reported-as-cancelled`): GitHub reports a timed-out job as `cancelled`, exactly like a manual cancel, so the apply job holds `actions: read` and `checks: read` and reads the agent job's check-run annotations; `cancelled` with an annotation containing `exceeded the maximum execution time` is a timeout and surfaces; `cancelled` without it only releases; if the annotations cannot be read, it surfaces (the safe side). Two signals are combined, and either one means timeout: the annotation, read across EVERY page of the annotations API; and the agent job's `started_at` / `completed_at` from the jobs API (which the agent cannot write) reaching the trusted `agentTimeoutMinutes` (a lock-job output, passed to the apply phase as `--agent-timeout-minutes`) minus a one-minute tolerance, because the job clock may start after `started_at`; erring there only surfaces the item to a human. The duration check is the backstop for the unmeasured cases (the agent flooding annotations, GitHub's per-job annotation cap). The apply job finds the agent job in the jobs API for this run attempt by the name suffix `/ agent` (inside a called workflow the job is named `<caller job> / agent`), and makes these reads with `GITHUB_TOKEN`, never `DORFL_GH_TOKEN`. Annotation text is agent-controllable: it is only substring-matched, never printed. A forged timeout annotation on a real cancel only surfaces the item to a human, which is the safe side.
6. **Git LFS.** Decided: full LFS support in this spec (not fail-closed). See task `ci-split-handoff-artifact-format` and task `ci-split-apply-rejects-hostile-bundle` for the handoff and the validation; the LFS path gets its own hostile-artifact tests.
7. **The continue-branch rebase push.** Decided: the agent job rebases the kept `work/task-<slug>` locally; the apply job pushes it with `--force-with-lease` against the tip the lock job observed (`continueTip`). The lock job does no rebase. This applies to the build path (`start.ts` in-place continue) and to the answered merge action (`workspace.ts` `createJob`).
8. **Install source for the write jobs in workspace mode** (dorfl's own repository). Decided: all three jobs build dorfl from the same base sha; the generated workflow comment states that in merge mode this runs code an earlier agent landed on `main` in the write jobs, which is the trust merge mode already implies.
9. **Old workflows with a new dorfl.** Decided: warn now (in GitHub Actions, when an agent-spawning verb runs without `--phase` in a checkout whose `.git/config` holds a credential), refuse in the next minor version.
10. **Intake shape.** Decided: `intake.yml` calls the same reusable per-item workflow with `item: issue:<N>`.
11. **Skipping the agent job when the rung needs none.** Decided: in the first cut. The lock job outputs `needsAgent: false` for an answered task/spec `apply` with no `kind: merge` entry, a `kind: stuck` answer, the observation surface short-circuit and an intake triage skip.
12. **Cache poisoning** (the agent can write default-branch cache entries through the runtime token; dorfl's own `release.yml` restores a pnpm cache in a job that can publish to npm). Decided: a separate task, filed before this spec's tasks land: `work/tasks/backlog/release-workflow-restores-no-cache.md`.

## Considered options

- **Harden the single job** (the dropped attempt above): every layer was bypassable while the agent shares the job.
- **A per-leg key binding a matrix leg's artifact** (a lock-job output used as a MAC key): measured not viable, because every value a job receives through `env:` is printed in its log, and a masked value is dropped from job outputs (decision 1 and the finding `github-actions-job-output-key-and-per-run-artifact-isolation`).

## Consequences

- Two extra jobs per item, plus a per-tick `dispatch` job and one Actions run per item; runs waiting in a slot cost no runner minutes.
- In merge mode most lands will be re-rebased after the gate ran (decision 2); the apply phase reports it.
- A task that edits a protected path (`.github/` and the rest of decision 3) can no longer land from CI; it is built locally (decision 4).
- The gate verdict and the Gate-2 verdict are attestations from the hostile job, which is no worse than before; the untrusted-origin forced PR (ADR `untrusted-origin-build-checkpoint`) stays the safety for untrusted work and is recomputed by the apply job.
